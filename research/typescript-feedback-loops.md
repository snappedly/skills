# TypeScript feedback loops for AI-assisted repositories

Research date: 17 September 2026

## Question

How should the feedback-loop ideas in [Essential AI Coding Feedback Loops For TypeScript Projects](https://www.aihero.dev/essential-ai-coding-feedback-loops-for-type-script-projects) be incorporated into the Snappedly skills, `setup-snappedly-skills`, and the Shipyard repository?

## Executive conclusion

The article is directionally right, but its four tools are not the reusable abstraction. The reusable abstraction should be a repository's **feedback-loop contract**: which command gives fast static feedback, which test scope is appropriate for the changed behavior, how formatting is applied, which broader checks are required for package or release changes, and where CI enforces the contract.

That contract belongs in the existing `docs/agents/workflow.md` configuration generated by `setup-snappedly-skills`. The existing `tdd`, `implement`, `code-cleanup`, and `build-local` skills already own most of the behavior that consumes it. A new top-level skill would initially duplicate those responsibilities and would not make agents use the checks automatically.

Shipyard should be the concrete reference implementation. It already has TypeScript typechecking, Vitest, Prettier, lint-staged, Husky, a build, and pull-request CI. The implementation makes the contract explicit and adds the missing CI formatting gate after repairing its formatting baseline. It keeps the full test suite out of the default pre-commit hook: the suite is useful feedback, but it takes about 27 seconds locally and is already a CI gate.

## What the article recommends

The article, updated 16 January 2026, presents four loops:

1. Add a TypeScript `typecheck` script, shown as `tsc`, for cheap static feedback.
2. Add automated tests, shown with Vitest, for logical errors.
3. Use Husky to run checks from a `pre-commit` hook.
4. Use lint-staged with Prettier to format staged files automatically; ESLint is mentioned as an optional additional task.

It also recommends making a running local development server reachable to the coding agent for frontend feedback. Its example hook runs lint-staged, typechecking, and tests in sequence. [Article source](https://www.aihero.dev/essential-ai-coding-feedback-loops-for-type-script-projects)

## First-party behavior behind the recommendations

The tools support the proposed split between fast local feedback and broader verification:

- TypeScript's `strict` option enables the strict family of type-checking options, and `noEmit` lets a check validate types without producing output. The repository should choose its own compiler command and configuration rather than blindly copying `tsc`. [TypeScript `strict`](https://www.typescriptlang.org/tsconfig/strict.html), [TypeScript `noEmit`](https://www.typescriptlang.org/tsconfig/noEmit.html)
- Vitest's `vitest run` runs tests once without watch mode. A repository can still pass a focused test file or other supported CLI options for a smaller loop. [Vitest guide](https://vitest.dev/guide/)
- Husky's recommended `husky init` creates a `.husky/pre-commit` script and updates `package.json`'s `prepare` script. Hooks are therefore a repository integration, not a property of the test framework. [Husky get started](https://typicode.github.io/husky/get-started.html)
- lint-staged selects staged files for configured globs, passes the matching paths to tasks, and automatically includes task modifications in the commit when the tasks succeed. Its JavaScript configuration can deliberately run a whole-project command such as `tsc --noEmit` without passing staged filenames. [lint-staged README](https://github.com/lint-staged/lint-staged#readme)
- Prettier's `--check` mode reports unformatted files and returns exit code `1`, which makes it suitable for CI. `--write` is the local autofix mode. [Prettier CLI](https://prettier.io/docs/cli)

These sources support the mechanics, but they do not imply that every TypeScript repository should use the same package manager, test framework, linter, hook policy, or full-suite threshold. Those choices belong to the repository contract.

## Recommended seam and ownership

The deep module is the **feedback-loop contract** recorded in `docs/agents/workflow.md`.

Its interface should answer:

- What command is the fastest reliable static check?
- What test command and scope apply to changed logic?
- What formatting/lint command is autofix versus read-only validation?
- When are build, full-suite, browser, migration, or release checks required?
- Which adapter enforces each check locally, in the agent workflow, and in CI?
- What evidence must be reported, and what is explicitly not applicable?

The implementations/adapters are the project's `package.json` scripts, TypeScript/Vitest/Prettier configuration, Git hooks, CI workflow, and—when relevant—the `build-local` preview. This gives agents one small interface to learn while allowing each repository to keep its own tools and risk policy.

## Recommended changes

### Snappedly skills

1. Extend `setup-snappedly-skills`'s exploration to inspect package scripts, lockfile/package manager, TypeScript config, test runner, formatter/linter, hooks, and CI. It should record what already exists before proposing changes.
2. Add an explicit “feedback loops” subsection to the `workflow.md` seed template. The default should recommend: format changed files, run the fastest static check, run focused tests for changed behavior, and broaden to build/full suite/release checks only when the change or repository policy requires it.
3. Have setup write the discovered commands and applicability into the existing `Required checks` section. Do not install Vitest, Prettier, Husky, or ESLint merely because a repository contains TypeScript; adding dependencies and hooks is a separate opt-in decision.
4. Keep `tdd` responsible for the red/green test loop and public-seam test quality. Keep `implement` and `code-cleanup` responsible for consuming the contract and returning evidence. Keep `build-local` responsible for the optional running-server/frontend loop.
5. Add a short verification line to the generated `AGENTS.md` summary only if it improves discoverability; the detailed contract remains in `docs/agents/workflow.md` so it has one source of truth.

For genuinely greenfield Snappedly repositories that should receive a standard TypeScript stack, a separate starter/preset is cleaner than making the generic setup skill install a stack. Setup configures policy; a starter owns dependencies and files.

### Shipyard

1. Preserve the current staged-formatting pre-commit adapter.
2. Consider adding `npm run typecheck` after lint-staged in `.husky/pre-commit`; its measured cost is small. Do not add `npm test` there initially.
3. Add a single fast verification script, for example `npm run check`, that runs `format:check`, `typecheck`, and the full test command in a clear sequence. Keep `build` as a separate required check for public package-output changes and CI.
4. Repair or intentionally scope the current formatting baseline, then run `npm run format:check` in pull-request CI. CI should continue to run the build and full test suite.
5. Do not add ESLint until Shipyard has an agreed rule set and a concrete failure mode it would catch. Prettier, TypeScript, tests, the public-declaration check, and CI currently provide a coherent loop.
6. Update shipped workflow prompts to point agents at the repository's configured check contract rather than assuming every consumer has the exact same `npm run typecheck` and `npm run test` scripts. Shipyard's own checks can remain concrete in its repository documentation.

## Rollout order

1. Update the skills contract and setup draft/template, with no dependency or hook installation.
2. Apply the concrete contract to Shipyard: baseline formatting, `check` script if accepted, local typecheck hook if accepted, and CI formatting enforcement.
3. Run setup against the next new repository and confirm that it discovers existing checks, records applicability, and asks before adding tooling.
4. Only create a dedicated starter or opt-in installer if repeated new-repo setup shows that teams want the same TypeScript dependencies and hook files.

This keeps policy reusable, automation explicit, and Shipyard useful as a tested example without forcing one TypeScript toolchain onto unrelated repositories.

# Deploy

Take the branch from "I'm happy with it" to merged. The user's invocation is the approval: it authorizes the commit, the push, the change request, and the merge within the repository's configured policy. Deploy stops at the merge and its closures; it does not run or approve a production release. Load each dependency named below through the available skill invocation mechanism or its installed `SKILL.md`; when one is not installed, follow the fallback given with it and report the missing skill as a gap.

Once the change request is registered with the harness, tell a pause from a stop. Step 4's wait for the watcher is a pause: keep the registration, end the turn, and resume when the watcher wakes you. Every other stop ends the run, including the final report: stop watching the change request first so control returns to the user.

Read `docs/agents/code-host.md` for the change-request and merge operations, `docs/agents/workflow.md` for the base branch, merge strategy, who merges, and the closure events, and, when the change request links tickets, `docs/agents/issue-tracker.md` for their operations. `workflow.md` is authoritative for the base branch and merge strategy; take each from `code-host.md` only when `workflow.md` does not record it. Reuse their unchanged contents from context. Without them, use the repository's contribution rules, the host CLI, and the host's default merge method.

Resolve the delivery base before changing branches: the user's branch argument, then the configured base branch, then the default branch. Record the intended changes from the user's request and any cleanup or review record. Keep cleanup's review base and checked commit so its batch can be distinguished from inherited branch history.

1. **Commit what is left.** On the resolved base branch or the default branch, or on a branch that already has a merged or closed change request, first create a new branch named for the change and move the uncommitted work there. Inspect staged, unstaged, and untracked files. Leave out files that are not part of the work, such as local environment files or generated output. Commit the rest to the current branch with a message in the repository's convention, letting hooks run. If a hook rejects the commit, report its output and stop. Done when `git status` shows nothing to commit that belongs to the work.
2. **Check the scope and push.**
   - **Sync.** Refresh the remote base and tracking branch. When the tracking branch has commits the local branch lacks, compare them with the local commits (for example with `git range-diff`) to tell genuinely new commits from ones the local branch rewrote by an amend or a local rebase. Replay only the genuinely new remote commits onto the local branch (for example with `git cherry-pick`), keeping the local versions of rewritten ones, and load and apply `resolving-merge-conflicts` for any conflict (without it, resolve each conflict preserving both sides' intent, and stop to ask when intent is unclear).
   - **Match the scope.** Compare the prospective change request's full patch and commit range against the intended changes. Existing divergence between the starting branch and delivery base stays outside the task unless explicitly included. If it adds unrelated changes, preserve the original branch, transplant only the intended batch onto a new branch from the resolved base, and report any open change request on the original branch so the user can close or retarget it. If the batch cannot be isolated without a scope or behavior decision, report that decision and stop before publishing.
   - **Cover the delivery.** Load and apply `code-cleanup` and then `code-review` to any transplanted or rebased result and to any delivered change that no cleanup or review record covers, such as the work step 1 committed, reusing only evidence whose inputs remain unchanged. With no cleanup or review record in the session, as when `/clean-up` ran in another session, that is the full delivery diff. Without `code-cleanup`, run the checks `workflow.md` requires (else the repository's formatter, linter, type check, and tests for the touched code) and inspect the diff for leftover debris; without `code-review`, review the full diff locally against the intended changes for correctness, requirements, and maintainability. Leave any cleanup edit uncommitted for `/clean-up`. When no fresh check record covers the head, run the checks `workflow.md` requires before publishing. Checks that require a push or an open change request belong to step 4.
   - **Push.** Push only once the delivery diff matches the intended scope, required pre-publication checks pass, cleanup made no edits, and review findings are resolved under repository policy; set the upstream when there is none. Otherwise stop before publishing, report what is unresolved and the decision each open finding needs, and recommend settling those in the conversation, then `/clean-up` and `/deploy` again. Use a force push with a lease only when the branch was rebased or rewritten and belongs to this work.

   Done when the remote branch matches the checked local one.
3. **Open or update the change request.** Find the open change request for this branch and use the resolved base. Load and apply `pr` to create one when none exists, or to refresh the title and description when the diff changed since it was written (without it, write the title per `docs/agents/code-host.md` and the description from the repository's pull request template). Mark a draft ready. When the harness tracks pull requests, register the change request with it so the harness can follow its checks and merge. Done when an open, non-draft change request targets the base, describes the current diff, and is registered with the harness when it supports that.
4. **Wait for checks.** With a harness pull-request watcher, hand the change request to it while checks run or an approval the user's account cannot give is outstanding: report what is pending, end the turn, and resume here when the watcher wakes you. Without one, poll for up to 15 minutes. Stop on a failing check, a conflict with the base, a review comment that asks for changes, or anything still pending when the poll ends: report what blocked it, and recommend fixing it in the conversation, then `/clean-up` and `/deploy` again. Done when every check has passed on the head, no review comment asks for changes, and the host reports the change request mergeable.
5. **Merge.** If the head changed since the scope check, or the change request now targets a different base, return to step 2 and follow the remaining steps for the resulting branch and change request; on a second such change, report it and stop. A base branch that only moved ahead needs no restart, since the host refuses a merge that is no longer clean. When `workflow.md` assigns the merge to a human, stop and report the change request ready for that merger, with step 6's closure events pending on the merge. Without `workflow.md`, when the repository shows that merging into the base deploys to production, such as a CI workflow that deploys on push to that branch or a hosting configuration whose production branch is the base, stop the same way: report the change request mergeable and that its merge would deploy, and recommend `/setup-snappedly-skills` to record the release policy. Otherwise merge with the configured operation and strategy, matched to the verified head commit. Verify the host's completed merge record for that head and target base, then confirm that the resulting merge commit, squash commit, or final rebased commit is in the remote base's history. Squash and rebase merges can replace the original head's identity. If the host reports success but the resulting commit cannot be verified, report the merge as unverified and stop before branch deletion or ticket closure; do not retry the merge. After verification, delete the remote head branch when the host has not already done so and it is a task branch this work created or one that exists only for this change request. Keep any other branch, such as the base or default branch, a protected branch, or a long-lived branch that `workflow.md` names or other change requests target, and say so. Update the local base branch when a checkout of it is clean. Done when the host reports the change request merged and its resulting commit is verified on the target base.
6. **Close out.** Verify each merge-time closure event `workflow.md` assigns to the agent or to provider automation: linked executable tickets closed, and the parent spec closed where the workflow closes it on this merge. Close each item assigned to the agent that is still open, then verify it. Report an item assigned to provider automation that did not transition, with its evidence, rather than closing it for the automation. When the spec stays open and every child ticket is now closed, do what `workflow.md` records for that moment: comment on the spec that it is ready for acceptance, or only report it; with nothing recorded, report it. Without a configured workflow, close only executable tickets the change request links with a closing keyword, such as `Closes #12`, leaving planning specs and merely mentioned items open, and report any parent whose children are all closed. Done when every merge-time transition assigned to the agent is verified, every one assigned to provider automation is verified or reported, and every transition assigned to a human is reported with its evidence.

Report the commit, the branch and base, the change request link, check results, the merge commit, ticket states, the delivered changes deploy cleaned up and reviewed itself, what `workflow.md` says happens next when it records a production release, and anything stopped or pending with its reason.

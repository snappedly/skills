# Execute

Carry out the plan this conversation settled on, or a tracker issue the user names, then clean up, review, and preview the result. You are the coordinator: you own the plan, the split into pieces, integration, review fixes, and the preview. Leave the combined changes uncommitted until an explicit commit request or `/deploy`; an explicit commit on the base or default branch first creates a task branch, as `/deploy` does. Load each dependency named below through the available skill invocation mechanism or its installed `SKILL.md`; when one is not installed, follow the fallback given with it and report the missing skill as a gap.

1. **Collect the plan.** Take it from the conversation: usually the change the agent most recently proposed in reply to the user, with any corrections the user made. When `grill` ran, include its settled decisions and the recommended answers the user did not override. When the user names a tracker issue, such as `/execute #42`, read it with its comments through the operations in `docs/agents/issue-tracker.md`, else the tracker's CLI: the plan is its agent brief when one is posted, else its body and discussion, and each acceptance criterion becomes a plan line and a requirement. Use any other arguments to narrow or adjust that plan. Treat the plan as approved and start without another confirmation round. Ask only when neither the conversation nor a named issue holds a plan, or two settled points contradict each other. List the plan in a few lines before starting. Done when every change to make has a line in that list.
2. **Split the work.** Read `docs/agents/workflow.md` when present for required checks and finding disposition. When the plan changes UI, read `docs/agents/frontend.md` when present, so the changes follow its design system, tokens, and visual direction. Then read the code each change touches. Group the plan into pieces. A piece owns a set of files and can be built and checked on its own. When two pieces share a file, a schema, an export, or another contract, merge them or make one wait for the other. A plan that forms one piece stays in this agent. Delegate each independent piece substantial enough to gain from its own worker, however many there are; small or mechanical pieces stay in this agent. Done when every plan line belongs to one piece, each piece is assigned to a worker or this agent, and every dependency between pieces is named.
3. **Run the pieces.** Launch one worker per ready delegated piece in parallel through the harness's sub-agent tool, each in its own git worktree snapshotted from the user's checkout, including uncommitted and untracked files. Leave the user's index and stash as they are. A fresh worktree lacks ignored files such as installed dependencies and local environment files: workers run the repository's setup command and report any check they cannot run there; credentials stay out of worktrees. Brief each worker with its plan lines, owned files, the contracts it must keep, the `frontend.md` conventions for a UI piece, and `tdd` for verification scope (without it, state the scope: test changed logic at existing seams and inspect presentation edits visually). A worker does its piece itself: implement, run its checks, inspect its diff, commit in the worktree, and return the commit, changed paths, check results, and blockers to you. That commit is a handoff; cleanup and review run once, in step 5. Meanwhile, build the pieces kept in this agent in the user's checkout. When a piece finishes, release the pieces waiting on it from a snapshot that includes its result, taken when no kept piece is mid-edit. Done when every delegated piece has returned a commit or a blocker, and every kept piece is built or blocked.
4. **Integrate.** Apply each worker's changes to the user's checkout as uncommitted changes, one piece at a time in dependency order. Load and apply `resolving-merge-conflicts` when a conflict needs judgment (without it, resolve the conflict preserving both sides' intent, and stop to ask when intent is unclear). Run the affected checks on the combined result and fix what integration broke. Remove each worker's worktree once its changes are in. Done when every piece is in the checkout, uncommitted, and the affected checks pass or each failure is recorded.
5. **Clean up and review.** Load and apply `code-cleanup` on the combined change, then `code-review` on the same scope. Supply the plan as the requirements and cleanup's check record as evidence. Without `code-cleanup`, run the checks `docs/agents/workflow.md` requires (else the repository's formatter, linter, type check, and tests for the touched code) and inspect the diff for leftover debris; without `code-review`, review the full diff locally against the plan for correctness, requirements, and maintainability. Fix findings in one batch as the workflow directs, rerun the affected checks, and recheck only the fix delta. Report findings that need a user decision, such as a heuristic concern, a waiver, or a requirement change. Done when cleanup's checks pass or each failure is recorded, every applicable review result has returned, and every finding is fixed or listed with the decision it needs.
6. **Open the preview.** When the changes affect something viewable, such as a web page, an app screen, or a docs site, start or reuse the project's development server from the user's checkout. Open the changed page in the harness's preview pane, else another browser tool, else give its local URL. Confirm the page shows the changes at the viewports `docs/agents/workflow.md` lists, else at a narrow mobile width and a desktop width, with a snapshot when the tools allow, and leave the server running. When nothing is viewable, say so in one line. Done when the preview shows the changed page or the report says why there is none.

Report each plan line with its status, the pieces and workers used, check results, review depth and findings with their dispositions, the preview location, and anything blocked or skipped. Close by recommending `/clean-up` for the final check and change report.
